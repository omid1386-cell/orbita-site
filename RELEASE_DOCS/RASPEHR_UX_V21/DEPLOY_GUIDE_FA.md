# راهنمای انتقال و انتشار رسپهر V21-RC1 — همه اصلاحات در یک بسته

**مخزن هدف:** `omid1386-cell/orbita-site`  
**مهم:** این بسته روی **مخزن موجود** اعمال می‌شود، نه یک مخزن خالی. فایل‌های دیگر را پاک نکنید.  
**هیچ کدام از گام‌های قبلی را جداگانه بارگذاری نکنید.** بسته V21 شامل اصلاحات گوگل مپس/گوگل ارث V16 و اصلاحات تجربه کاربری V17 تا V21 است.

## یک بار بارگذاری؛ گام به گام
1. از مخزن موجود GitHub **پشتیبان/شاخه** بگیرید و آخرین commit را برای برگشت احتمالی نگه دارید. اگر GitHub Pages یا Render روی `main` Auto Deploy دارند، **روی main مستقیم کار نکنید**.
2. ZIP نهایی را در رایانه استخراج کنید. پوشه `UPLOAD_TO_REPO_ROOT` را پیدا کنید.
3. از GitHub Desktop یا دستور Git، مخزن را Clone کنید و یک شاخه جدید مثلا `release/raspehr-v21-ux` بسازید.
4. **فقط محتویات داخلی** `UPLOAD_TO_REPO_ROOT` را به ریشه مخزن Clone شده (همان جایی که `index.html` قرار دارد) کپی کنید، به‌گونه‌ای که فایل‌ها در مسیرهای فعلی جایگزین شوند. **خود پوشه `UPLOAD_TO_REPO_ROOT` نباید به مخزن برود.**
5. تفاوت فایل‌های تغییرکرده را در GitHub Desktop ببینید. اگر فایل‌های مخزن بعد از نسخه مبنا مستقلا اصلاح شده‌اند، آن‌ها را کورکورانه جایگزین نکنید؛ موارد تعارض را ادغام کنید. این بسته نباید داده‌های به‌روزشونده مستقل (`data/upcoming_global.json` و `data/upcoming_global_landings.json`) را حذف یا جایگزین کند.
6. داخل ریشه مخزن، کنترل زیر را اجرا کنید: `python RELEASE_DOCS/RASPEHR_UX_V21/verify_release.py`؛ نتیجه مورد انتظار `PASS` است. برای آزمون‌های فنی: `node --test tests/upcoming-event-theme-parity-v21.test.cjs` و `node --test raspehr-3d/tests/*.test.cjs`؛ خروجی سه‌بعدی با ۱ شکست **آگاهانه ممیزی V9** در V21 مستند شده است.
7. Commit و Push را در شاخه جداگانه انجام دهید و سپس Pull Request باز کنید. **پیش از ادغام در main** روی یک محیط آزمایشی یا Preview (اگر فراهم است) رفتار را بررسی کنید. ادغام در main ممکن است به‌صورت خودکار انتشار عمومی را فعال کند.
8. پس از تأیید در محیط آزمایشی، شاخه را با `main` ادغام کنید تا سرویس متصل GitHub Pages/Render به‌روزرسانی شود.

## نکته بسیار مهم درباره Render
فایل `render.yaml` پروژه برای سرویس `orbita-report-api` است، نه سایت نقشه. سرویس اصلی، Static Site است. **هیچ تنظیم مربوط به وب‌سرویس گزارش یا اسرار آن را تغییر ندهید.** اگر سرویس سایت به GitHub متصل است، از همان سرویس و تنظیمات موجود استفاده کنید.

## فهرست پذیرش پس از انتشار
- در موبایل و دسکتاپ، دکمه نمای سه‌بعدی نباید روی شناسنامه کشور یا گالری بیفتد؛ فقط یک دکمه بازگشت به نقشه دوبعدی وجود داشته باشد.
- در دسکتاپ، پرتاب‌های پیش‌رو از نوار بالای سایت باز شود؛ فرودهای پیش‌رو هم کار کنند؛ موبایل دچار رگرسیون نشده باشد.
- بازشدن شناسنامه کشور در اولین مراجعه و مراجعات بعدی سریع باشد و آمار و متن همان قبلی باقی بماند.
- در نقشه سه‌بعدی، کاوش خلوت باشد؛ کارت مکان در دسکتاپ در پنل کناری و در موبایل در Bottom Sheet نمایش داده شود؛ کنترل‌های زوم روی پنل قرار نگیرند.
- تب‌های پرتاب و فرود هر دو تم سرمه‌ای تیره هماهنگ داشته باشند، حتی با تغییر تم عمومی سایت به روشن.
- فیلترهای ۱/۲ هفته و ۱/۴ ماه، فیلتر چندکشوری و مبنای انتساب کشور در هر دو پنجره درست کار کنند؛ «فرود» روز را نشان دهد، نه ساعت ساختگی.
- منوی «مشاهده در نقشه‌های دیگر» برای پایگاه، شرکت و بازیابی، لینک‌های موقعیت/ماهواره‌ای/ارث را داشته باشد؛ بسته به دسترسی شبکه، سرویس بیرونی ممکن است باز نشود.
- کش: در بخش Network بارگذاری فایل‌های `assets/js/app.js?_t=20261127-ux-v21` و `assets/css/raspehr-event-parity-v21.css?v=20261127-ux-v21` را کنترل کنید.

## بازگشت امن در صورت اختلال
اگر عملکرد حیاتی خراب شد، از commit سالم پیش از ادغام یک **revert commit** در شاخه جدید بسازید و PR بازگشت ایجاد کنید. از Force Push روی main و پاک‌کردن فایل‌های به‌روزشونده داده خودداری کنید. روی Render نیز آخرین نسخه سالم را مجددا Deploy کنید. اگر مشکل فقط مربوط به محدودیت دسترسی Google Earth در بعضی شبکه‌هاست، کل سایت را بی‌دلیل برنگردانید.

**محدودیت:** مرورگر محلی تأییدیه بارگذاری WebGL واقعی یا محیط عمومی نیست. انتشار عمومی پس از آزمون سایت/مرورگر واقعی تصمیم‌گیری می‌شود.
